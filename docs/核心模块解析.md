### 2.3 重点目录说明

#### `network/`

公共底层模块，所有服务都依赖它，包含：

- `core/`：Netty server/client 基础封装
- `rpc/`：自研 RPC 框架
- `db/`：数据库访问、实体类、SQL
- `config/`：配置加载
- `utils/`：日志、ID、类扫描、内存检测等

#### `gen/`

代码生成模块，包含：

- `genProto/proto/`：`.proto` 协议定义
- `genProto/gen/`：生成后的 Java 协议类
- `genRpc/gen/CallEnum.java`：RPC 方法编号枚举
- `genDb/`：数据库实体生成工具

#### `game/`

真正的服务实现模块，内部又分为多个进程功能区：

- `external/`：对外服，接客户端 TCP / WS
- `game/`：核心业务服，玩家对象、模块、协议处理
- `global/`：跨服公共服务，如聊天、好友、邮件、玩家简要信息
- `http/`：客户端取对外服地址的 HTTP 服务
- `gmback/`：GM 后台服务

#### `client/`

包含两个客户端入口：

- `sendmsg.main.ClientStartUp`：消息发送工具
- `bot.main.BotStartUp`：机器人工具

#### `admin-ui/`

GM 后台前端静态页面，登录页和业务页面都在这里，GM 后台服务启动后会直接挂载该目录作为静态资源。

#### `start/`

包含启动脚本：

- `start/windows/server_run_all.bat`
- `start/linux/server_run_all.sh`

## 3.2 各服务职责

### 1）CenterServer

中心服是所有 RPC 节点的注册中心。

职责：

- 接收各节点上报
- 维护当前在线节点信息
- 将新节点信息广播给旧节点
- 让各 RPC 节点彼此建立连接

### 2）ExternalServer

对外服负责接入真实客户端。

职责：

- 监听 TCP / WebSocket 端口
- 验证客户端首包
- 为每个连接分配连接 ID
- 将客户端消息转发到对应的 Game 节点
- 接收 Game 服 RPC 返回，再发回客户端

### 3）GameServer

业务服是玩家会话与核心玩法的执行者。

职责：

- 登录流程
- 加载 / 创建玩家对象
- 玩家消息队列处理
- 玩家模块生命周期管理
- 定时保存玩家数据
- 调用 Global 服完成跨服业务
- 响应 GM 后台命令

### 4）GlobalServer

全局服用于承接跨玩家、跨逻辑服共享的公共能力。

当前已有模块：

- `ChatService`：聊天历史与广播
- `FriendService`：好友关系与申请
- `MailService`：邮件与附件
- `PlayerInfoService`：玩家简要信息

### 5）HttpServer

HTTP 服务主要给客户端分配对外服地址。

职责：

- 提供 `/external_address`
- 提供 `/external_address_list`
- 接收对外服的心跳上报
- 尽量给同一个 uid 维持同一 external 地址

### 6）GmBackServer

GM 后台服务，既提供后台登录与管理接口，也负责和 game 服做 GM 指令同步。

职责：

- `/api/login` 登录认证
- 节点监控
- 热更配置
- 发邮件
- 踢人
- 封禁 / 禁言名单广播
- 用户与操作日志管理

## 5. 协议与消息结构

## 5.1 外层消息结构

客户端与服务器之间业务消息统一使用 `TopicProto.MBasePacketData`：

```protobuf
message MBasePacketData {
  TOPIC packet_type = 1; // 模块类型
  uint32 packet_id = 2;  // 模块内消息 ID
  bytes packet_data = 3; // protobuf 消息体
}
```

含义：

- `packet_type`：模块，例如登录、背包、好友
- `packet_id`：模块内具体消息编号
- `packet_data`：该消息对应的 protobuf 二进制内容

## 5.2 TOPIC 模块枚举

当前 `packet.proto` 中主要定义：

- `TOPIC_TYPE_LOGIN`
- `TOPIC_TYPE_HUMAN`
- `TOPIC_TYPE_CHAT`
- `TOPIC_TYPE_MAP`
- `TOPIC_TYPE_MINER`
- `TOPIC_TYPE_ITEM`
- `TOPIC_TYPE_TASK`
- `TOPIC_TYPE_FRIEND`
- `TOPIC_TYPE_MAIL`
- `TOPIC_TYPE_ACTIVITY`

## 5.3 网络包结构

在 TCP / WebSocket 层，最终传输的是 `SocketMessage`：

```text
4 字节 messageType
4 字节 dataLength
N 字节 data
```

其中：

- `messageType=0`：idle
- `messageType=1`：biz

客户端业务数据 `data` 本体就是 `MBasePacketData` 的二进制。

## 5.4 协议命名规则

以登录模块为例：

- 客户端枚举：`FROM_CLIENT.C2S_Login`
- 服务端枚举：`FROM_SERVER.S2C_Login`
- 客户端 message：`MC2S_Login`
- 服务端 message：`MS2C_Login`

框架通过命名约定自动反射解析协议类，因此：

- `TOPIC_TYPE_TASK` -> `TaskProto`
- `C2S_AcceptTask` -> `MC2S_AcceptTask`

必须遵循规范。

## 6. 客户端与服务器通讯流程

## 6.1 获取对外服地址

客户端启动时先读取：

- `config/client-config.properties`
- `http.address`
- `http.port`
- `client.socket=tcp|websocket`

然后通过：

```text
GET /external_address?type=tcp&uid=xxx
```

或：

```text
GET /external_address?type=websocket&uid=xxx
```

获取返回：

```json
{
  "address": "127.0.0.1:10000"
}
```

分配逻辑：

- HTTP 服务维护 external 地址池
- 同一个 uid 优先分配之前的 external
- 如果旧 external 不可用，则随机分配一个新的

## 6.2 建立客户端连接

客户端拿到地址后：

- TCP 模式：连接 `ip:port`
- WebSocket 模式：连接 `ws://ip:port`

连接建立后首包不是 protobuf，而是字符串认证：

```text
CLIENT_CONNECT_
```

对外服验证通过后，为客户端分配一个 `connectionId`。

## 6.3 external 与 game 的绑定

首次 external 向 game 转发客户端消息时，会把自己的 RPC 节点 ID 一起发过去。

首次 game 向 external 回包时，也会把自己的 RPC 节点 ID 带回。

这样后续：

- external 知道这个连接属于哪个 game 节点
- game 知道这个玩家当前挂在哪个 external 节点

实现“客户端消息 -> 定向 game 节点”和“game 消息 -> 定向 external 节点”的双向绑定。

## 6.4 登录流程

### Step 1：客户端发送登录协议

```text
TOPIC_TYPE_LOGIN + C2S_Login
```

消息体：

```protobuf
message MC2S_Login {
  string uid = 1;
}
```

### Step 2：game 服创建或加载 account

game 收到登录协议后：

- 先检查 `uid -> accountId` 缓存
- 无缓存则查 `account` 表
- 查不到则新建账号
- 回包 `S2C_Login`

### Step 3：客户端自动请求角色列表

客户端收到 `S2C_Login` 后，自动发：

```text
C2S_HumanList
```

### Step 4：game 返回角色列表

- 查询 `human_list`
- 返回 `S2C_HumanList`

### Step 5：客户端自动选择角色

默认发送：

```text
C2S_SelectHuman(pos=0, server_id=1)
```

### Step 6：game 加载或创建角色

- 若该位置角色不存在：创建新角色、初始化模块并落库
- 若角色已存在：加载 `human_info.role_data`
- 发送 `S2C_SelectHuman`
- 再发送 `HumanInfo + 各模块 sendToClient() + SendInfoEnd`

### Step 7：登录完成后心跳

客户端 / bot 会定时发送：

```text
C2S_ClientPing
```

game 回：

```text
S2C_ClientPing
```

若超过 60 秒未收到 Ping，game 会把玩家加入下线清理队列。

## 6.5 登录后业务消息流

登录后的客户端消息流程：

```text
Client
  -> ExternalServerHandler
  -> ClientConnection.msgQueue
  -> ExternalRecvMessageService.pulse()
  -> RPC: GameRecvMessageService.recvMessage
  -> HumanObject.msgQueue
  -> GameMasterService.pulseHandlerHumanMsg
  -> LogicUtils.handler
  -> XxxMsgHandler
  -> XxxModule / RpcFunction / System
  -> ConnectObject.sendMsg
  -> RPC: ExternalRecvMessageService.recvMessage
  -> ExternalServer -> Client
```

这个链路是整个项目最核心的运行时主路径。
